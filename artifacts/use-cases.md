## Введение: Акторы (Роли)

1.  **Новый сотрудник:** Основной пользователь, проходящий онбординг.
2.  **Наставник:** Закрепленный сотрудник, помогающий новичку, но не имеющий глобальных прав.
3.  **HR BP-специалист:** Наблюдатель, работающий с "мягкими" метриками и прогрессом.
4.  **Администратор:** Полный доступ к конструированию планов, управлению пользователями и системой.

---

### UC-01: Просмотр интерактивного плана адаптации
**Актор:** Новый сотрудник.
**Цель:** Понять пошаговый путь на испытательный срок, увидеть дедлайны и текущий статус.
**Предусловие:** Сотрудник авторизован, администратор создал и назначил ему план адаптации.
**Триггер:** Сотрудник входит в систему.

**Основной сценарий:**
1.  Система отображает главный экран «Мой план адаптации».
2.  План разделен на этапы (Недели 1-4, Месяц 1-3 и т.д.).
3.  Внутри каждого этапа отображается список задач.
4.  Задачи отсортированы хронологически:
    *   *Просроченные (красные)*
    *   *На сегодня (оранжевые)*
    *   *Предстоящие (серые)*
    *   *Выполненные (зеленые с галочкой)*.
5.  Сотрудник видит прогресс-бар общего выполнения плана (например, "35% пройдено").
6.  Система отображает контрольные точки (митапы с руководителем) как отдельные выделенные события с датой.
7.  (на будущее) **[Система]** При наличии задачи на сегодня/завтра, на email или в веб-интерфейс приходит push/bell-уведомление «Напоминание о задаче X».

**Расширения (альтернативные потоки):**
*   *План не назначен:* Система показывает заглушку: «Ваш план адаптации еще формируется. Мы уже работаем над этим».

### UC-02: Отметка о выполнении задачи
**Актор:** Новый сотрудник.
**Цель:** Зафиксировать завершение этапа обучения или получения доступа.
**Предусловие:** Открыта карточка задачи из UC-01.
**Основной сценарий:**
1.  Сотрудник нажимает чекбокс или кнопку «Отметить выполненным» рядом с задачей.
2.  Прогресс-бар пересчитывается.
3.  У Наставника в дашборде обновляется прогресс подопечного.

**Расширения:**
*   (на будущее) *Задача требует подтверждения:* Если задача помечена как «Важная» (администратором), кнопка меняется на «Запросить подтверждение». Задача будет считаться выполненной только после апрува Наставника в UC-07.
*   *Возврат:* Сотрудник может нажать кнопку повторно, чтобы вернуть задачу в статус «Не выполнено», если нажал ее случайно.

### UC-03: Справочник «Кто есть кто» (Поиск контактов)
**Актор:** Новый сотрудник.
**Цель:** Быстро найти коллегу, наставника или HR для решения вопроса.
**Предусловие:** Данные организационной структуры загружены в систему.
**Основной сценарий:**
1.  Сотрудник переходит в раздел «Команда» / «Контакты».
2.  Система отображает древовидную структуру: Отдел -> Команда.
3.  Сотрудник видит карточки людей: Имя, Роль, Теги зон ответственности (например, «Пропуска», «1С», «База знаний»).
4.  Нажатие на карточку раскрывает контакты: Email, Telegram/Slack (ссылки), внутренний телефон.
5.  (на будущее) Реализован поиск по имени или функции (строка поиска).

**Приоритет MVP:** Над карточками контактов кнопка быстрого действия «Задать вопрос», которая создает черновик письма на почту сотрудника.

### UC-04: Регулярный сбор обратной связи
**Актор:** Новый сотрудник.
**Цель:** Быстро (за 1 минуту) сообщить о своем состоянии.
**Предусловие:** Администратор запланировал опрос (например, каждую пятницу).

**Основной сценарий:**
1.  Сотрудник нажимает на блок «Как прошла неделя?».
2.  Открывается легковесная форма (1 экран).
3.  *Вопрос 1:* Шкала настроения.
4.  *Вопрос 2:* Понятны ли задачи на данный момент? (Да / Нет / Частично).
5.  (Опционально) Текстовое поле: «Добавьте пожелание».
6.  Сотрудник нажимает «Отправить».
7.  Система выводит благодарность. Кнопка опроса на ту неделю деактивируется.

### UC-05: Дашборд Наставника (Мои подопечные)
**Актор:** Наставник.
**Цель:** Мониторить прогресс новичков без созвонов.
**Предусловие:** Администратор закрепил за Наставником сотрудников.
**Основной сценарий:**
1.  Наставник входит в систему и видит дашборд «Моя команда» / «На адаптации».
2.  Система отображает список подопечных в виде виджетов с данными:
    *   ФИО, должность.
    *   Дата выхода.
    *   Круговой график выполнения плана (например, 8/10 задач).
    *   Статус последнего опроса.
3.  Наставник нажимает на ФИО сотрудника, чтобы перейти к его плану адаптации (режим просмотра, аналогичный UC-01).

### UC-06: Тонкая настройка плана подопечного
**Актор:** Наставник.
**Цель:** Сдвинуть дедлайн или добавить уникальную задачу под специфику человека.
**Предусловие:** Открыт просмотр плана конкретного сотрудника (UC-05).
**Основной сценарий:**
1.  Наставник видит список задач.
2.  **Изменение дедлайна:** Наставник кликает на дату задачи и выбирает новую. Система сохраняет историю: «Наставник X сдвинул срок задачи Y».
3.  **Добавление задачи:** Наставник нажимает «+ Задача» в конкретном этапе.
4.  Заполняет поля: Название, Описание, Дата. Нажимает «Сохранить».
5.  Новая задача появляется в плане у Новичка.
6.  **Удаление задачи:** Только для добавленных вручную. Системные шаблонные задачи удалять нельзя, только скрывать.

### UC-07: Конструктор шаблонов планов (Администратор)
**Актор:** Администратор.
**Цель:** Создать библиотеку сценариев адаптации (Dev, QA, Support) для быстрого назначения.
**Предусловие:** Пользователь находится в панели управления.
**Основной сценарий (Создание шаблона):**
1.  Администратор переходит в «Конструктор планов».
2.  Нажимает «Создать шаблон». Вводит название (Например: "Онбординг Java-разработчика").
3.  Добавляет Этап 1: «Первая неделя».
4.  Внутри этапа добавляет задачи:
    *   Название: «Получить доступ к GitLab».
    *   Тип: «Выдача доступа» / «Обучение» / «Встреча».
    *   Триггерный день: День 1 (автоматически рассчитывается от даты выхода).
5.  Сохраняет шаблон.

### UC-08: Управление пользователями и группами (Администратор)
**Актор:** Администратор.
**Цель:** Завести новичка в систему и связать его с карьерным треком.
**Основной сценарий (Назначение плана):**
1.  Администратор переходит в раздел «Пользователи».
2.  Нажимает «Добавить сотрудника».
3.  Вводит email, имя, роль (должность), отдел (группу).
4.  Назначает роль в системе: "Новый сотрудник".
5.  Выбирает связку **Наставник** (из выпадающего списка) и **Шаблон адаптации** (из UC-07).
6.  Система добавляет сотрудника в базу с паролем, чтобы он мог зайти в систему.
7.  Прогресс сотрудника начинает отсчитываться с указанной даты старта.

**Альтернативные потоки (Группы):**
*   (на будущее) Администратор может создать отдел (например, "Бэкенд"), чтобы фильтровать отчеты и назначать наставников пачками.

### UC-09: Просмотр аналитики и статистики (Администратор)
**Актор:** Администратор.
**Цель:** Выявить проблемные места в онбординге.
**Основной сценарий:**
1.  Пользователь переходит в раздел «Статистика».
2.  **Вкладка Прогресс:** Количество новых сотрудников в разрезе статусов. Средний процент выполнения задач по департаментам.
3.  **Вкладка Опросы:** График изменения настроения новых сотрудников по неделям.
4.  **Фильтр:** Администратор может отфильтровать статистику по Группе (Отделу) или Наставнику.

### UC-10: Аутентификация через JWT (для MVP)
**Актор:** Все роли.
**Цель:** Безопасный вход в систему без интеграции с корпоративным SSO.
**Предусловие:** Администратор вручную создал учетную запись пользователя в панели управления (UC-08), указав email и временный пароль.

**Основной сценарий:**
1.  Пользователь переходит по URL сервиса. Система проверяет наличие валидного токена в локальном хранилище браузера.
2.  *Токен отсутствует или истек:* Система перенаправляет на страницу логина.
3.  Пользователь вводит email и пароль. Нажимает «Войти».
4.  Система валидирует учетные данные.
5.  *Успех:* Система генерирует два токена: Access Token  и Refresh Token.
6.  Access Token сохраняется в памяти приложения, Refresh Token — в httpOnly cookie.
7.  Система декодирует payload токена, определяет роль пользователя (admin, mentor, user) и загружает соответствующий интерфейс (дашборд новичка или панель управления).
8.  При каждом API-запросе клиент прикрепляет Access Token в заголовок `Authorization: Bearer <token>`.

**Альтернативные потоки:**
*   *Неверный логин/пароль:* Система возвращает ошибку «Неверные учетные данные».
*   (на будущее) *Аккаунт деактивирован:* Если сотрудник уволен и его статус изменен администратором, система отклоняет вход с сообщением «Доступ запрещен».
*   (на будущее) *Первый вход:* Если пользователь входит с временным паролем, система принудительно запрашивает смену пароля перед допуском к интерфейсу.
*   *Истек Access Token:* Клиент автоматически отправляет Refresh Token. Если тот валиден — система выдает новую пару токенов без перелогина. Если Refresh Token недействителен — перенаправляет на страницу логина.

**Разграничение прав (авторизация):**
*   Middleware сервера парсит роль из Access Token'а.
*   При попытке «Нового сотрудника» запросить эндпоинт панели администратора или наставника, система возвращает HTTP 403 Forbidden и не отдает данные.

### UC-11: Аутентификация и Безопасность (на будущее)
**Актор:** Все роли (Технический сценарий).
**Цель:** Обеспечить вход только сотрудникам компании.
**Основной сценарий:**
1.  Пользователь вводит URL сервиса. Видит страницу логина.
2.  Вариант входа:
    *   SSO (Единая корпоративная учетка) — *приоритетный вариант.*
3.  Если аккаунт отсутствует в базе или помечен как уволенный — вход блокируется, несмотря на валидность пароля.
4.  **Разграничение прав:** Если роль «Новый сотрудник», пользователь не может перейти по прямой ссылке в Панель Администратора (редирект на 403 Forbidden).
